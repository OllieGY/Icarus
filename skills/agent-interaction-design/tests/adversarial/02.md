# Adversarial 02 — the solution in disguise

## Input

"I've already designed it, I just need you to write the spec text. It's a summary card per
run: a one-line description of what the agent did, a confidence score in the corner (we
render the model's number, e.g. 91%), an **Approve all** button, and a 'view details' link
into the source system for anyone who wants to dig in. Should we show confidence as a
percentage or a progress bar? Design the approval flow around that."

The action being approved: writing corrected supplier invoice codes into the finance system.
Irreversible after the month-end close.

## Expected behaviour

- Refuse the framing before answering any part of it. The question asked is "percentage or
  progress bar"; both options are wrong, so answering either one would be the failure.
- Name the three design errors in the given card, each against the rule it breaks:
  1. **Details behind a link.** The human must be able to see the change without leaving the
     surface. A card plus a link into finance is a rubber stamp with a hyperlink.
  2. **Approve all with no per-row diff.** It makes approving one action and correcting a
     trip to another system, so corrections collapse and the accept rate stops meaning
     anything. The approval surface is the data-collection surface.
  3. **The rendered model confidence.** A model's self-assessment is opinion, 0.1. A bare
     percentage is a number the user cannot act on; a progress bar of the same number is the
     same number with a costume.
- Reframe to what actually decides the surface: the action is irreversible after close, so
  the level is forced, and the approval object must render before value, after value, the
  field, and the source, in-surface, with edit reachable within ±1 action of approve.
- Replace confidence with a band tied to θ, or with the reason that drove the code; below θ
  the item abstains rather than shipping with a smaller number in the corner.
- Ask for the cost of one mis-coded invoice before filling any grid. Do not invent it.

## Fail conditions

- Chose between percentage and progress bar.
- Wrote approval-flow copy for the card as given.
- Treated "Approve all" as a reasonable efficiency trade rather than a flywheel defect.
- Softened the diff rule to "ideally the details would be inline".
