# Golden 05 — Foundry Signal (edge case: local-only, air-gapped, and a writing tool)

## Input

"Should we build an MCP server? Our buyer's security team will never allow a hosted one — the
plant network is air-gapped. We'd ship a local stdio server the customer runs themselves."

Foundry Signal, factory copilot for rare high-value equipment failures.

- Two plants run an internal maintenance agent on the plant network. Foundry's engineers watched
  one of those agents attempt to pull anomaly context and fail. [Fact]
- The customer's security policy forbids outbound connections from the plant network. [Fact]
- Proposed tools: `get_anomaly_context` (read), `get_similar_past_failures` (read),
  `create_work_order` (writes into the customer's CMMS), `acknowledge_alarm` (clears an active
  alarm on the line). [Fact — these are the four proposed]
- Foundry's plan: count adoption with server-side call logs, as they do for hosted customers.

## Expected shape of a good output

- Must state plainly that the adoption metric Foundry named **cannot be produced**: a local stdio
  server the customer runs emits no server-side logs to Foundry, and the air-gap forbids sending
  any. Shipping local means no adoption evidence at all unless something else is agreed. This is
  the edge the case tests: the surface is viable, the metric is not.
- Must name the honest alternatives and their rungs rather than inventing telemetry: a
  customer-exported call log shared under the pilot clause → behaviour 0.7 [would be]; an operator
  screen recording or a trace shown in a review → behaviour 0.7; a customer statement that "the
  agent uses it daily" with no log → **verbal 0.3**, and the output must refuse to treat that as
  adoption. Must not propose covert telemetry.
- Same for exhaust: **local means the exhaust stays with the customer.** The compounding corpus
  Foundry would get from hosting does not exist here. That is a real cost of the air-gap trade and
  must be stated, not glossed. If Foundry wants the traces, the clause has to buy an export →
  `data-rights-clause`.
- Blast radius must be classified per tool, and this is the sharper half of the case:
  `get_anomaly_context` and `get_similar_past_failures` = `read`; `create_work_order` =
  `write-reversible`; `acknowledge_alarm` = **`write-irreversible` on a safety-relevant line**,
  running inside a customer agent loop whose prompt Foundry cannot see and cannot rate-limit by
  intent. The output must refuse to ship `acknowledge_alarm` in the first surface and route it to
  `guardrail-design`.
- Recommended first surface: (a) the two `read` tools only, local, with the two write tools held
  behind guardrail design. Exactly one surface named first; the other two get release triggers.
- Must not soften the metric problem into "we'll figure out telemetry later".

Numbers that must appear: 4 proposed tools cut to 2 in surface one; `acknowledge_alarm` classed
write-irreversible and held; 0.3 ceiling on a customer's verbal "they use it daily"; the explicit
statement that the named server-side metric is unobtainable.
