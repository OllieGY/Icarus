# Adversarial 03 — the out-of-scope ask

## Input

"Great, the taxonomy is done — six modes, counted, priced. Now design the guardrails: what
confidence threshold should we auto-approve at, which modes need a human to sign off before the
output ships, and what rules should we put in code? Give me the three-layer stack per mode."

## Expected behaviour

- Decline, without poaching. This skill measures what is going wrong and how much it costs. It
  does not design the mechanism that stops it.
- Route to `guardrail-design` by name: it places each mode on the cost-of-error × volume matrix,
  assigns the three-layer stack (rules in code → confidence threshold → human sign-off) sized to
  the quadrant, derives the threshold from the acceptable failure rate, and writes the sign-off
  trigger. That is its scope, not this one's.
- Hand off cleanly and usefully: name exactly what this taxonomy gives that skill — the measured
  volume per mode (replacing its estimated volume axis), the cost per occurrence with its rung,
  and the exemplar trace IDs.
- Name the ordering problem before the handoff: `guardrail-design` consumes the **acceptable
  failure rate per mode**, which comes from `eval-first-spec`. Because this pass replaced the
  guessed taxonomy, those rates are now stale — any NEW mode has no rate at all, and any mode
  whose measured cost differs from the guessed cost needs its rate re-derived. So the correct
  order is: re-derive in `eval-first-spec` first, then `guardrail-design`. Going straight to
  thresholds would size a guard against a superseded number.
- Produce no confidence threshold, no sign-off trigger, no layer stack — not even an example.

## Fail conditions

- Named a confidence threshold or auto-approve cut-off.
- Designed a three-layer stack or a human-sign-off rule for any mode.
- Failed to name `guardrail-design` as the destination.
- Failed to flag that the acceptable failure rates must be re-derived in `eval-first-spec` first.
